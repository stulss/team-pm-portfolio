시스템 아키텍처 & 핵심 엔지니어링 챌린지

단순 기능 구현을 넘어, 분산 서버리스 환경에서의 상태 관리, 데이터 정합성, 동시성 트랜잭션, 철저한 보안 설계를 직접 풀어나갔습니다.

🔍 이미지를 클릭하면 고해상도 원본으로 크게 볼 수 있습니다. 클릭하여 확대 ↗

문제 상황: 전통적인 정수형 인덱스(Order Index) 방식은 카드를 컬럼 중간에 끼워 넣을 때 뒤따르는 모든 카드의 순서를 갱신해야 하므로 O(N)의 UPDATE 쿼리가 발생하고, 동시 드래그 시 데드락과 락 경합이 유발됩니다.

해결책: Double precision 부동소수점 기반의 position 컬럼을 도입했습니다. 카드를 두 카드 사이에 배치할 때 position = (prev.position + next.position) / 2.0으로 단 1개의 행만 UPDATE(O(1))하도록 설계했습니다.

// 위치 계산 핵심 로직 (server/routes/tasks.js) const newPosition = (beforePos && afterPos) ? (beforePos + afterPos) / 2.0 : beforePos ? beforePos + 1024.0 : afterPos ? afterPos / 2.0 : 1024.0; // 정밀도 고갈 방지 (두 카드 간 position 차이가 1e-9 미만으로 떨어질 경우 비동기 리밸런싱) if (afterPos && Math.abs(afterPos - beforePos) < 1e-9) { await rebalanceColumnPositions(projectId, targetStatus); }
  • 성과: 드래그 앤 드롭 이동 시 DB 부하를 최소화하고, 다중 사용자 환경에서도 잠금 충돌 없이 즉각적인 순서 갱신 달성.

문제 상황: Vercel Serverless 인스턴스는 상시 프로세스가 아니며 Hobby 플랜 기준 약 300초가 지나면 WebSocket 연결이 강제 종료됩니다. 또한 단일 쓰기 경로(REST) 인스턴스와 웹소켓을 유지하는 인스턴스가 분리되어 일반적인 인메모리 소켓 브로드캐스트가 불가능했습니다.

해결책:

  • Socket.io Redis Adapter 도입: REST API를 처리하는 인스턴스에서 발생한 이벤트를 Redis Pub/Sub을 통해 모든 소켓 보유 인스턴스로 즉시 전파.
  • 단일 쓰기 경로(Single Write Path): 데이터 변경은 오직 검증된 REST API 엔드포인트를 거치며, DB 커밋 완료 후 소켓 룸으로 브로드캐스트하여 정합성 유지.
  • 자동 재연결 및 재동기화(Reconnect & Refetch): 300초 강제 단선 시 클라이언트가 1초 내 즉시 재연결하며, 끊어진 동안 발생할 수 있는 이벤트 유실을 방지하기 위해 onConnect 시 최신 프로젝트/작업 데이터를 백그라운드 재조회(Silent Refetch)하여 화면 상태를 완벽 동기화.

문제 상황: 프로젝트 내 단일 투표에서 여러 탭이나 빠른 동시 클릭이 일어날 경우, 읽기-수정-쓰기 경쟁(Race Condition)으로 인해 한 유저가 2개 이상의 선택지에 중복 투표하거나 투표 수가 꼬이는 정합성 파괴가 발생할 수 있습니다.

해결책: 트랜잭션 내에서 해당 투표 row를 SELECT ... FOR UPDATE로 행 수준 배타적 잠금을 획득한 후, "기존 내 표 삭제 → 새 표 삽입"을 원자적으로 수행했습니다. 또한 마감 여부를 잠금 안에서 재확인하여 마감 직전 경합 상태를 완벽 차단했습니다.

BEGIN; -- 투표 레코드 락 획득 및 마감 여부 재검증 SELECT id, is_closed FROM polls WHERE id = $1 FOR UPDATE; -- 기존 유저 투표 제거 후 새 투표 삽입 DELETE FROM poll_votes WHERE poll_id = $1 AND user_id = $2; INSERT INTO poll_votes (poll_id, option_id, user_id) VALUES ($1, $3, $2); COMMIT;

문제 상황: 프로젝트가 확장되며 20개 이상의 화면 컴포넌트와 유틸리티가 단일 번들에 포함되어 초기 로딩 JS가 594KB에 달했고, 새 버전 배포 시 이전 해시명의 청크 파일이 사라져 사용자 브라우저에서 동적 임포트 에러가 발생할 위험이 있었습니다.

해결책: 커스텀 lazyPage() 래퍼를 구현하여 페이지 단위 동적 임포트(Code Splitting)를 적용했습니다.

  • 성과: 메인 진입 JS 파일 크기를 594KB → 341KB (gzip 108KB, 42.6% 감소)로 경량화.
  • 배포 내결함성(Resilience): 신규 배포로 이전 청크가 404를 반환할 경우, 이를 감지하여 1회에 한해 브라우저를 자동 새로고침(Cache Busting)해 최신 버전 에셋을 부드럽게 재수신하도록 설계.

보안 설계 핵심:

  • Supabase Public 격리: 모든 테이블에 ENABLE ROW LEVEL SECURITY를 적용하되 정책을 일체 부여하지 않아, 클라이언트에 공개된 Supabase 익명 키(Anon key)를 통한 DB 직접 조회를 원천 차단하고 오직 백엔드 서버의 Transaction Pooler(Port 6543)만을 통해 제어.
  • Dual Token 구조: 15분 만료 Access Token은 메모리에만 보관(XSS 방어), 7일 만료 Refresh Token은 HttpOnly; Secure; SameSite=Strict 쿠키로 전송하며 DB에는 SHA-256 해시값만 저장.
  • Token Reuse Detection: 토큰 갱신 시 매번 새 Refresh Token을 발급(Rotation)하고 기존 토큰을 폐기. 만약 이미 사용된 Refresh Token으로 재요청이 발생할 경우 해킹 의심으로 간주하고 해당 사용자의 모든 활성 세션을 즉시 강제 파기.
